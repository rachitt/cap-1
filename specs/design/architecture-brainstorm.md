## Part 2 — Open at design time, resolved here

### DD-10 — Uniform error envelope

**Options.** (a) FastAPI default `{"detail": ...}`; (b) RFC 7807 problem+json; (c) a bespoke
envelope carrying `error_code`.

**Chosen: (c), shaped so it is a superset of what the client needs.**

```json
{
  "error": {
    "code": "INSUFFICIENT_FUNDS",
    "message": "Transfer declined: available balance is lower than the requested amount.",
    "field_errors": [{"field": "amount", "message": "..."}],
    "correlation_id": "01J8Z..."
  }
}
```

**Rationale.** `E1-S1` requires every `DomainError` subclass to carry a machine-readable
`error_code`. That attribute is worthless if the API layer discards it — the UI must be able to
distinguish `INSUFFICIENT_FUNDS` from a generic 422 without string-matching prose, because
`AC-05` is graded on that specific failure being unmistakable. `field_errors` is nullable and
present only for validation failures. `correlation_id` closes the loop with NFR-06 structured
logging: a user reporting a failure can quote one id that appears verbatim in the log stream.
RFC 7807 was rejected only because its `type` URI field is dead weight for a local, single-app
deployment — the shape is otherwise equivalent.

**Every 4xx and 5xx response in `api-contracts.md` uses this envelope. No exceptions.**

### DD-11 — Pagination shape

**Options.** (a) offset/limit with a total count; (b) cursor/keyset; (c) page/size with a total.

**Chosen: (c) `?page=1&size=20`, response `{items, page, size, total, total_pages}`.**

**Rationale.** Assumption A-06 already fixes default size 20, most-recent-first. Statements are
the only paginated collection with meaningful volume and they are read by a human scrubbing
backwards through a list, which is exactly the access pattern page numbers serve. Keyset paging
buys stable pagination under concurrent insert — real, but the volume here is seeded synthetic
data and the cost is a UI that cannot show "page 3 of 7". `total` is affordable because SQLite
`COUNT(*)` over a per-account index is trivial at this scale. Cap `size` at 100 so an unbounded
list is structurally impossible.

### DD-12 — Frontend type generation

**Options.** (a) hand-maintained TypeScript interfaces; (b) generate from the FastAPI OpenAPI
document at build time; (c) share a schema-first IDL.

**Chosen: (b).** `openapi-typescript` reads `/openapi.json` and emits
`frontend/src/lib/api/schema.d.ts`, which is committed and regenerated by a script. BRD §7.1 names
Pydantic/TypeScript drift as the one real disadvantage of Option A and names generation as the
mitigation; making drift structurally impossible is worth one npm script. `E6-S1` already
carries "generated API types" in its title.

**Consequence for the planner:** money fields arrive in TypeScript as `string`. The frontend
formats them and performs no arithmetic on them. Say this explicitly in `data-models.md`.

### DD-13 — Where the transfer destination comes from

**This is the invented-rule trap. Read carefully.**

`AC-04` says "transfer money to another account". It does **not** say "to a saved beneficiary".
Beneficiaries are `AC-06`, an independent convenience feature. The BRD withdrew the beneficiary
precondition explicitly (A-03) and the dependency graph deliberately omits the `E4-S2 → E4-S4`
edge (DR-17). Stories now carry negative assertions that grep for beneficiary-precondition
identifiers and require zero matches.

**Therefore:** `POST /api/v1/transfers` accepts a destination **account number** directly. The
request body carries `destination_account_number`, not `beneficiary_id`. The transfer screen
offers saved beneficiaries as an optional autofill affordance — a shortcut that writes into the
account-number field — and the field remains directly editable at all times. There is no code
path, schema constraint, or UI state in which a transfer requires a beneficiary to exist.

### DD-14 — Four rules that must NOT appear anywhere

Reintroducing any of these fails a story test. They are listed here so the planner can grep its
own output before writing it:

1. **No transfer cap, daily limit, or velocity control.** No `max_transfer_amount`,
   `daily_limit`, `velocity`, `CapExceeded`.
2. **No beneficiary precondition on transfers.** See DD-13. No `NotBeneficiaryError`.
3. **No applicant age or date-of-birth eligibility gate.** `date_of_birth` is captured as
   profile data and consumed by nothing.
4. **No loan eligibility computation.** No principal bounds, no tenure bounds, no income
   threshold, no instalment-to-income ratio, no credit score, no risk band, no
   `EligibilityError`. `declared_monthly_income` is optional and informational; no rule reads
   it. Loan approval is an administrator decision (AC-08). The only loan validation that exists
   is **structural**: principal > 0 with at most 2 decimal places, tenure a positive whole
   number of months, and the legal state-transition matrix.

Where the brief is silent, stay silent. Model the field as optional and informational, or omit
it entirely.

### DD-15 — Audit entry `metadata_json`

**Chosen:** a JSON object column, written by the caller, never queried by a `WHERE` predicate
on its interior. Filtering in `GET /api/v1/admin/audit` is by first-class indexed columns only:
`action`, `entity_type`, `entity_id`, `actor_id`, `occurred_at` range. Keeping metadata opaque
means the audit module stays generic — it accepts
`(actor, action, entity_type, entity_id, metadata)` and imports nothing from transfers or loans,
which is precisely what breaks the audit/transaction dependency cycle (dependency-graph.md).

### DD-16 — Money on the wire, stated as a schema constraint

Not prose — a constraint the evaluator can test. Every money field in both `.schema.json` files:

```json
{"type": "string", "pattern": "^-?\\d{1,16}(\\.\\d{1,2})?$", "examples": ["0.00", "1234.56"]}
```

In the OpenAPI document the same fields are `{"type": "string", "format": "decimal", "pattern": ...}`.
A JSON *number* anywhere a money value appears is a contract violation and the evaluator should
flag it as such.

### DD-17 — Health endpoint placement

`GET /health`, **unversioned and outside `/api/v1`**, because it is infrastructure rather than
product surface and `project-manifest.json` hard-codes `http://localhost:8000/health` in three
places (`evaluation.health_check`, `verification.health_check.url`). It performs a trivial DB
round-trip and returns within 1s (NFR-07).

### DD-18 — Correlation ID propagation

Generated at middleware entry if the client did not supply `X-Correlation-ID`; echoed on every
response header; carried into every log line and into every `audit_entries.correlation_id`.
Header name is `X-Correlation-ID` on both request and response. This makes NFR-06 assertable
end to end and gives the audit ledger a join key back to the log stream.

### DD-19 — Soft delete for beneficiaries

`deleted_at` nullable timestamp (A-07). List endpoints filter `deleted_at IS NULL`. Historical
transaction and audit rows keep referring to the row. `DELETE /api/v1/beneficiaries/{id}`
returns 204 and is idempotent on an already-deleted row only to the extent of returning 404 —
the row is gone from the caller's view.

### DD-20 — Design identity for Horizon Bank

No brand exists; the identity is invented and must not read as a framework default —
`design_quality` and `originality` are weighted 1.5x with a floor of 5 and an overall threshold
of 8 (`calibration-profile.json`). Direction: **trustworthy financial software, not fintech
novelty**. A restrained palette anchored on a deep ink/navy with a single decisive accent;
generous whitespace; a tabular-figures typeface for every money value so digits align in
columns; state colour used only for state (success, warning, danger) and never decoratively; no
gradient on a balance, no ambiguity on a failure. Money is the loudest thing on any screen it
appears on. Tokens are recorded once and reused by every mockup.

## Part 3 — Standing constraints for both agents

- Mobile-first. Breakpoints 375 / 768 / 1440. At least one genuinely responsive layout (brief §7.2).
- WCAG 2.1 AA: contrast on all text and every money value, semantic landmarks, visible focus
  rings, programmatically associated labels and error messages, `aria-live` on transfer
  success/failure.
- Synthetic data only. No real names, no real account numbers, nothing that could be mistaken
  for a live record.
- The 40 stories in `specs/stories/` and the 267 features in root `features.json` are the
  routing targets. `component-map.md` must cover all 40 story IDs.
