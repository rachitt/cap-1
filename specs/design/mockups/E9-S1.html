E9-S1 · evaluator tooling

UI verification map

This page is not a product screen. It is the contract between the mockups and the Playwright MCP suite: which selector on which screen proves which acceptance criterion. Every data-testid below appears verbatim in the mockup it names, so a verification run can be written against the mockups today and re-pointed at the running application unchanged.

Selector policy

Prefer the accessible query first — role and accessible name — because it verifies the semantics a real user depends on. Fall back to data-testid only where the accessible name is ambiguous across repeated rows, or where the element is a container rather than a control. Never select on a CSS class or a DOM path: both are styling concerns and will churn.

04 · Journeys

The money-conservation run

F248 is the one journey that cannot be faked by a screenshot: the browser must observe that money is conserved across a transfer. It reads both balances from the DOM before and after, using the selectors below.

F248 — end-to-end transfer asserts money conservation in the browser
StepSelectorAssertion
1. Sign in as the seeded funded customer login-email login-password login-submit Dashboard renders; token stored
2. Record both balances account-balance (per account-card) Capture the two rendered strings verbatim — do not parse them into numbers in the assertion helper without a decimal library
3. Send a known amount transfer-destination-account-number transfer-amount transfer-review-button transfer-confirm-button Destination typed directly, with no saved payee selected
4. Observe the outcome transfer-success transfer-live-region Success state visible; live region announces it
5. Re-read both balances account-balance Source decreased by exactly the amount, destination increased by exactly the amount, and their sum is unchanged

What must not be findable

These are negative assertions. Each corresponds to a rule that was explicitly withdrawn, and each must return zero matches across every screen.

  • No text matching /daily limit|transfer cap|remaining allowance|max transfer/i
  • No control or copy asserting a beneficiary is required before a transfer; transfer-destination-account-number must be enabled and editable when beneficiaries-empty-state is showing
  • No request body field named beneficiary_id on the transfer call
  • No age, date-of-birth or eligibility validation message on register-date-of-birth
  • No text matching /eligib|you may qualify|credit score|risk band|affordab|instal?ment.to.income/i on E6-S5 or E7-S1
  • No money value rendered as a bare JSON number in any fixture

05 · Configuration & evidence

Playwright MCP, and the proof it ran

AC1 — .mcp.json at the repository root

Must parse as valid JSON and declare a Playwright MCP server with a runnable command.

{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["@playwright/mcp@latest"]
    }
  }
}

AC2 — configuration alone is not enough

An evaluator run must leave an artefact under specs/reviews/ recording the MCP-driven verification and its outcome, and naming at least one screen verified through MCP rather than through a direct HTTP call.

  • Which screen was opened, at which viewport
  • Which selectors from this map were queried
  • The pass or fail outcome per acceptance criterion
  • The axe violation count by impact
  • The snapshot diff result for all three breakpoints
