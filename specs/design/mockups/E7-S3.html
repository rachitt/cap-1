E7-S3 · responsive & accessibility

Conformance

Three widths, one layout system. Customer journeys are designed at 375 first and widen; the two administrator tables are designed at 1440 first and reflow to stacked cards rather than scrolling sideways. Nothing on any screen requires a horizontal scroll at any breakpoint.

01 · Breakpoints

Customer dashboard — E6-S3 at three widths

One column becomes two becomes three. The balance stays the largest element on the card at every width, and every tap target keeps its 44px minimum.

02 · Breakpoints

Administrator table — E7-S2 reflow

Below 768px the table stops being a table. Each row becomes a card and each cell carries its column name from data-label, so the reading order stays intact for both sighted users and screen readers. No horizontal scroll container is ever introduced.

03 · Colour

Measured contrast, every token pair in use

Ratios are computed from the token hexes against the surface each token actually renders on. Text must reach 4.5:1; non-text UI boundaries and focus indicators must reach 3:1.

One token is deliberately not for text

--ink-400 #74869B reaches 3.43:1 on paper. That clears the 3:1 required of a control boundary but not the 4.5:1 required of body text, so it is used only for input and button borders and never for a character of text. Decorative hairlines use --ink-200, which carries no information and is not subject to a contrast minimum.

04 · Accessibility

Conformance checklist

Structure and semantics

  • ✓Landmarks on every screen. header, nav with an accessible name, main, footer. Verified by F220.
  • ✓Exactly one h1. Headings descend without skipping a level; section headings are real h2/h3, never styled paragraphs.
  • ✓Every input has a programmatic label. label[for] pointing at the control id. No placeholder-as-label anywhere.
  • ✓Errors are bound to their input. aria-describedby extends to include the error element, and aria-invalid="true" is set on the control.
  • ✓Tables are real tables. th[scope="col"] on every header, a caption on every table, and the caption survives the mobile reflow.
  • ✓Status is never colour alone. Every badge carries its status as text plus a shape marker; direction carries a sign glyph and the words DEBIT or CREDIT.
  • ✓Icons are decorative. Every inline SVG is aria-hidden="true" focusable="false" and sits beside a text label; no icon carries meaning on its own.

Operability

  • ✓Visible focus, never the browser default. 3px --focus #0B57D0 ring at 2px offset on light surfaces, --focus-dark #8FBBFF inside ink regions. Applied through :focus-visible so it appears for keyboard use.
  • ✓44px minimum target on every button, link-button and form control at every breakpoint; 38px only for dense secondary row actions on the desktop-first admin tables, which also remain keyboard-reachable.
  • ✓Logical tab order follows the visual order because the DOM order is the visual order — no positive tabindex exists anywhere.
  • ✓The decision dialog traps focus using a native <dialog> with showModal(), which also gives Escape-to-close for free.
  • ✓Focus moves to the outcome. After a transfer or a loan decision, focus is placed on the resulting message so a keyboard user is not left at the top of the page wondering what happened.
  • ✓Motion respects the user. All transitions and the skeleton shimmer collapse to 0.001ms under prefers-reduced-motion: reduce.
  • ✓Text inputs are 16px. Below that, iOS Safari zooms the viewport on focus, which is itself a reflow failure.

05 · Keyboard

The two flows that must work without a mouse

Transfer, end to end

E6-S4 · verified by F218

  1. Tab to transfer-source-account; choose the source with the arrow keys. The balance beside it updates.
  2. Tab to transfer-destination-account-number and type the twelve digits. No payee needs to exist and none needs to be selected.
  3. Optionally Tab into transfer-beneficiary-shortcut and press Enter on a payee — it writes into the field above, which stays editable.
  4. Tab to transfer-amount, type the amount, then to transfer-description.
  5. Enter on transfer-review-button. Focus moves to transfer-confirm-button inside the confirm panel.
  6. Enter to send. Focus moves to the outcome message, and transfer-live-region announces it. On failure the message is role="alert".

Loan review, end to end

E7-S1 · verified by F219

  1. Tab to loan-queue-filter-status; change it with the arrow keys. The queue re-queries and loan-queue-live-region announces the new count.
  2. Tab into the table body. Each row’s applicant name is a button that opens loan-detail-panel.
  3. Enter on loan-action-approve. The native <dialog> opens modally and focus lands in decision-reason.
  4. Type the reason. Escape closes the dialog and returns focus; Tab reaches decision-submit.
  5. Enter with an empty reason: nothing is sent, decision-error-reason-required appears, and focus returns to the textarea.
  6. Enter with a real reason: the dialog closes, the row status updates in place, and focus moves to the resulting status message.
