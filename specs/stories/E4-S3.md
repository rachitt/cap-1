## Description

The second cross-cutting module, consumed by both E4 and E5. Notifications are enqueued inside the business transaction so they cannot be lost, but dispatched outside it so a stub gateway failure never rolls back committed money movement (DR-21, edge case E-18). Per DR-31 they are persisted to a table and emitted as a structured log line.

## Acceptance Criteria

**AC1.** `enqueue(customer_id, channel, event_type, payload)` writes a notification row with `status = QUEUED` inside the caller's transaction, and the row is rolled back if the enclosing transaction fails.

| Feature | Category | Verifies |
|---|---|---|
| `F102` | functional | Enqueued notifications are written as QUEUED within the caller's transaction |
| `F103` | integration | A rolled-back transaction leaves no orphan notification row |

**AC2.** `dispatch` marks a QUEUED notification `SENT` with a `sent_at` timestamp and emits a structured JSON log line carrying the `event_type` and correlation ID, satisfying both halves of DR-31.

| Feature | Category | Verifies |
|---|---|---|
| `F104` | functional | Dispatch transitions a notification to SENT with a timestamp |
| `F105` | functional | Dispatch emits a structured JSON log line naming the event type |

**AC3.** A dispatch failure marks the notification `FAILED` and does not raise into the caller, so an already-committed transfer stands (DR-21, edge case E-18).

| Feature | Category | Verifies |
|---|---|---|
| `F106` | integration | A failing dispatcher marks the notification FAILED without rolling back committed business state |

**AC4.** Both `EMAIL` and `SMS` channels are accepted by the same stub dispatcher and produce rows distinguishable by the `channel` column (assumption A-09).

| Feature | Category | Verifies |
|---|---|---|
| `F107` | functional | The stub dispatcher serves both EMAIL and SMS channels with distinguishable rows |

## Verification Steps

**`F102` — Enqueued notifications are written as QUEUED within the caller's transaction** _(AC1, functional)_

1. Inside a transaction, call enqueue with channel='EMAIL' and event_type='TRANSFER_COMPLETED', then commit
1. Query the notifications table for that customer
1. Assert one row exists with status == NotificationStatus.QUEUED and sent_at is None

**`F103` — A rolled-back transaction leaves no orphan notification row** _(AC1, integration)_

1. Open a transaction, call enqueue, then raise an exception before commit
1. Catch the exception outside the transaction scope
1. Query the notifications table in a new session and assert zero rows exist

**`F104` — Dispatch transitions a notification to SENT with a timestamp** _(AC2, functional)_

1. Enqueue a notification and commit, then call dispatch on it
1. Re-read the row and assert status == NotificationStatus.SENT
1. Assert sent_at is a non-null datetime

**`F105` — Dispatch emits a structured JSON log line naming the event type** _(AC2, functional)_

1. Capture log output while dispatching a notification with event_type='TRANSFER_COMPLETED'
1. Parse the captured lines as JSON
1. Assert at least one record contains event_type == 'TRANSFER_COMPLETED'
1. Assert the record also carries a correlation_id key

**`F106` — A failing dispatcher marks the notification FAILED without rolling back committed business state** _(AC3, integration)_

1. Complete and commit a transfer that enqueues a notification
1. Force the stub dispatcher to raise, then run dispatch
1. Assert no exception propagates to the caller
1. Assert the notification status is FAILED and both account balances are unchanged from their committed values

**`F107` — The stub dispatcher serves both EMAIL and SMS channels with distinguishable rows** _(AC4, functional)_

1. Enqueue one notification with channel='EMAIL' and one with channel='SMS' for the same customer
1. Dispatch both and assert each reaches status SENT
1. Assert querying by channel returns exactly one row for each value
