## Description

Persistence for the loan application and its immutable transition history. Per DR-26 every state change is appended to loan_state_transitions recording actor, reason and timestamp; that table has no update or delete path, mirroring the audit ledger. The queue query supports filtering by status for the admin review screen.

## Acceptance Criteria

**AC1.** `create_application` persists a loan with `status = APPLIED`, a `Decimal` principal and an integer tenure, and returns it with a non-null id (AC-07).

| Feature | Category | Verifies |
|---|---|---|
| `F133` | functional | A created loan application starts in APPLIED status with Decimal principal preserved |

**AC2.** `append_transition(loan_id, from_status, to_status, actor_id, reason)` writes one immutable row with a server-assigned timestamp, and the repository exposes no method to update or delete a transition (DR-26).

| Feature | Category | Verifies |
|---|---|---|
| `F134` | functional | Appending a loan transition writes one row recording actor, reason and timestamp |
| `F135` | security | The loan transition history exposes no update or delete path |

**AC3.** `list_transitions(loan_id)` returns the full ordered history oldest-first, so a loan that moved APPLIED → UNDER_REVIEW → APPROVED returns exactly three status values in chronological order.

| Feature | Category | Verifies |
|---|---|---|
| `F136` | functional | Transition history is returned in chronological order |

**AC4.** `list_by_status(status)` returns only loans in that status, backing the admin pending queue, and `list_for_customer(customer_id)` returns only that customer's loans (DR-12).

| Feature | Category | Verifies |
|---|---|---|
| `F137` | functional | Loans can be filtered by status for the admin queue |
| `F138` | security | Customer loan listing is scoped to the owning customer |

## Verification Steps

**`F133` — A created loan application starts in APPLIED status with Decimal principal preserved** _(AC1, functional)_

1. Call create_application with principal=Decimal('5000.00') and tenure_months=24 for an existing customer
1. Assert the returned record has a non-null id and status == LoanStatus.APPLIED
1. Re-read the row in a new session and assert principal == Decimal('5000.00') and isinstance(principal, Decimal)
1. Assert tenure_months == 24

**`F134` — Appending a loan transition writes one row recording actor, reason and timestamp** _(AC2, functional)_

1. Append a transition from APPLIED to UNDER_REVIEW with an admin actor_id and reason
1. Query loan_state_transitions for that loan_id and assert exactly one row exists
1. Assert the row records from_status, to_status, actor_id, reason and a non-null created_at

**`F135` — The loan transition history exposes no update or delete path** _(AC2, security)_

1. Introspect the loan repository public methods
1. Assert no method name related to transitions contains 'update', 'delete' or 'remove'
1. Run: grep -niE 'def .*(update|delete).*transition' backend/src/repository/loan_repository.py and assert no matches

**`F136` — Transition history is returned in chronological order** _(AC3, functional)_

1. Append transitions APPLIED→UNDER_REVIEW then UNDER_REVIEW→APPROVED for one loan
1. Call list_transitions for that loan id
1. Assert exactly 2 transition rows are returned
1. Assert the first row's to_status is UNDER_REVIEW and the second's is APPROVED

**`F137` — Loans can be filtered by status for the admin queue** _(AC4, functional)_

1. Create three loans and move one to UNDER_REVIEW
1. Call list_by_status(LoanStatus.APPLIED) and assert exactly 2 rows are returned
1. Call list_by_status(LoanStatus.UNDER_REVIEW) and assert exactly 1 row is returned

**`F138` — Customer loan listing is scoped to the owning customer** _(AC4, security)_

1. Create one loan for customer A and one for customer B
1. Call list_for_customer with A's id
1. Assert exactly one loan is returned and it belongs to A
1. Assert B's loan id is absent from the result
