## Description

Delivers the browser half of AC-04, AC-05 and AC-06. Beneficiaries are a saved-payee convenience: the transfer screen offers a saved payee as a shortcut but also accepts a directly entered destination account number, because DR-17 states beneficiaries do not gate transfers. The insufficient-funds state must be unmistakable and announced to assistive technology.

## Acceptance Criteria

**AC1.** The beneficiaries screen lists saved payees and supports add and remove, reflecting the change in the list without a page reload (AC-06).

| Feature | Category | Verifies |
|---|---|---|
| `F188` | ui | Adding a beneficiary appends it to the rendered list |
| `F189` | ui | Removing a beneficiary removes it from the rendered list |

**AC2.** The transfer screen accepts a destination either by selecting a saved beneficiary or by entering an account number directly, and both paths submit successfully (DR-17, AC-04).

| Feature | Category | Verifies |
|---|---|---|
| `F190` | ui | A transfer can be submitted by selecting a saved beneficiary |
| `F191` | ui | A transfer can be submitted to a directly entered non-beneficiary account number |

**AC3.** A 422 response carrying `INSUFFICIENT_FUNDS` renders an unmistakable failure state that names insufficient funds, is announced via `aria-live`, and leaves the displayed balance unchanged (AC-05).

| Feature | Category | Verifies |
|---|---|---|
| `F192` | ui | An insufficient-funds response renders a distinct, explicitly worded failure state |
| `F193` | ui | Transfer success and failure outcomes are announced through an aria-live region |

**AC4.** The amount input rejects entry of more than two decimal places or a non-positive amount before submission, and the confirm step displays the exact amount and destination being sent (DR-14).

| Feature | Category | Verifies |
|---|---|---|
| `F194` | ui | Client-side validation blocks over-precision and non-positive transfer amounts |
| `F195` | ui | The confirm step restates the exact amount and destination before submission |

## Verification Steps

**`F188` — Adding a beneficiary appends it to the rendered list** _(AC1, ui)_

1. Render the Beneficiaries screen with the list endpoint mocked to return one payee
1. Submit the add form with the create endpoint mocked to return 201
1. Assert POST /api/v1/beneficiaries was called with the entered nickname and account number
1. Assert the new payee appears in the rendered list

**`F189` — Removing a beneficiary removes it from the rendered list** _(AC1, ui)_

1. Render the Beneficiaries screen with two saved payees
1. Activate the remove control on the first payee with the endpoint mocked to return 204
1. Assert DELETE /api/v1/beneficiaries/{id} was called
1. Assert the removed payee is no longer rendered and one payee remains

**`F190` — A transfer can be submitted by selecting a saved beneficiary** _(AC2, ui)_

1. Render the Transfer screen with one saved beneficiary available
1. Select the saved beneficiary, enter amount '250.00' and confirm
1. Assert POST /api/v1/transfers was called with that beneficiary's destination account number
1. Assert a success state is rendered on a 201 response

**`F191` — A transfer can be submitted to a directly entered non-beneficiary account number** _(AC2, ui)_

1. Render the Transfer screen and enter a destination account number directly without selecting a saved payee
1. Enter amount '50.00' and confirm with the endpoint mocked to return 201
1. Assert POST /api/v1/transfers was called with the entered account number
1. Assert a success state is rendered and no message claims a beneficiary is required

**`F192` — An insufficient-funds response renders a distinct, explicitly worded failure state** _(AC3, ui)_

1. Submit a transfer with the endpoint mocked to return 422 and error code INSUFFICIENT_FUNDS
1. Assert a failure state is rendered whose text names insufficient funds
1. Assert the failure state is visually distinct from the success state
1. Assert the displayed source balance is unchanged from before the attempt

**`F193` — Transfer success and failure outcomes are announced through an aria-live region** _(AC3, ui)_

1. Render the Transfer screen and assert an element with aria-live is present
1. Submit a transfer that succeeds and assert the live region content names the success
1. Submit a transfer that fails with INSUFFICIENT_FUNDS and assert the live region content names the failure

**`F194` — Client-side validation blocks over-precision and non-positive transfer amounts** _(AC4, ui)_

1. Enter amount '10.001' in the Transfer form and attempt to confirm
1. Assert a validation message is rendered and no API call was made
1. Enter amount '0' and attempt to confirm, asserting a validation message and no API call
1. Enter amount '10.00' and assert confirmation proceeds

**`F195` — The confirm step restates the exact amount and destination before submission** _(AC4, ui)_

1. Enter a destination and amount '250.00' then advance to the confirm step
1. Assert the confirm step displays the formatted amount '250.00'
1. Assert it displays the destination account identifier being credited
