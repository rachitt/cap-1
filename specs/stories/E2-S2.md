## Description

Persistence for the two onboarding entities. The customer repository enforces email uniqueness at the database level so a duplicate registration surfaces as a constraint violation rather than a race-dependent read-then-write check. The KYC repository records submissions and verdicts.

## Acceptance Criteria

**AC1.** `create_customer` persists a customer with `status = PENDING_KYC` and `role = CUSTOMER` by default, and returns the row with a generated non-null `id`.

| Feature | Category | Verifies |
|---|---|---|
| `F038` | functional | A newly created customer defaults to PENDING_KYC status and CUSTOMER role |

**AC2.** The `customers.email` column carries a UNIQUE constraint: inserting a second customer with an email already present raises an integrity error and leaves the row count unchanged.

| Feature | Category | Verifies |
|---|---|---|
| `F039` | functional | Duplicate customer email insertion raises an integrity error and creates no second row |

**AC3.** `get_by_email` returns the matching customer and returns `None` for an unknown address rather than raising, so the auth service can produce a uniform 401 without leaking account existence.

| Feature | Category | Verifies |
|---|---|---|
| `F040` | security | get_by_email returns None for an unknown address instead of raising |

**AC4.** The KYC repository persists a record linked to `customer_id` with `status = PENDING`, and `mark_verified` / `mark_rejected` set the status, `verified_at` timestamp and `stub_reason` on that record.

| Feature | Category | Verifies |
|---|---|---|
| `F041` | functional | KYC records are created as PENDING and transition to VERIFIED with a timestamp |
| `F042` | functional | A rejected KYC record stores the stub_reason supplied by the policy |

## Verification Steps

**`F038` — A newly created customer defaults to PENDING_KYC status and CUSTOMER role** _(AC1, functional)_

1. Call create_customer with a unique email, password_hash, full_name and date_of_birth
1. Assert the returned record has a non-null id
1. Assert status == CustomerStatus.PENDING_KYC and role == Role.CUSTOMER
1. Re-read the row by id in a new session and assert the same status persists

**`F039` — Duplicate customer email insertion raises an integrity error and creates no second row** _(AC2, functional)_

1. Create a customer with email 'dup@horizon.test'
1. Attempt to create a second customer with the same email inside pytest.raises(IntegrityError)
1. Assert the error is raised
1. Query the customers table for that email and assert exactly one row exists

**`F040` — get_by_email returns None for an unknown address instead of raising** _(AC3, security)_

1. Call get_by_email('nobody@horizon.test') against an empty table
1. Assert the return value is None and no exception is raised
1. Create a customer and call get_by_email with its address
1. Assert the returned record id matches the created customer

**`F041` — KYC records are created as PENDING and transition to VERIFIED with a timestamp** _(AC4, functional)_

1. Create a customer, then create a KYC record for that customer_id
1. Assert the record status is KycStatus.PENDING and verified_at is None
1. Call mark_verified on the record and re-read it
1. Assert status is VERIFIED and verified_at is a non-null datetime

**`F042` — A rejected KYC record stores the stub_reason supplied by the policy** _(AC4, functional)_

1. Create a PENDING KYC record and call mark_rejected with stub_reason='RESERVED_TEST_DOCUMENT'
1. Re-read the record in a new session
1. Assert status is KycStatus.REJECTED and stub_reason == 'RESERVED_TEST_DOCUMENT'
