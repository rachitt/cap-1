## Description

Delivers the browser half of AC-09 and the administrator view of AC-10. Both are strictly read-only tabular surfaces over the append-only ledger and the notification log. The audit viewer must make clear that entries cannot be edited, reinforcing NFR-02 in the interface as well as the database.

## Acceptance Criteria

**AC1.** The audit viewer renders entries from `GET /api/v1/admin/audit` showing timestamp, actor, action, entity type and entity reference, covering both transactions and loan transitions (AC-09, DR-29).

| Feature | Category | Verifies |
|---|---|---|
| `F210` | ui | The audit viewer renders all required columns for each ledger entry |

**AC2.** The audit viewer offers filters for entity type, actor and date range that re-query the endpoint with the selected values (AC-09).

| Feature | Category | Verifies |
|---|---|---|
| `F211` | ui | Audit filters re-query the endpoint with the chosen entity type and date range |

**AC3.** The audit viewer is strictly read-only: it renders no edit or delete control for any entry, and a grep of the component finds no mutating API call (NFR-02, DR-28).

| Feature | Category | Verifies |
|---|---|---|
| `F212` | security | The audit viewer exposes no edit or delete affordance |

**AC4.** The notification viewer renders entries from `GET /api/v1/admin/notifications` with channel, event type and status, including both transfer and loan transition events (AC-10).

| Feature | Category | Verifies |
|---|---|---|
| `F213` | ui | The notification viewer renders channel, event type and status for each entry |
| `F214` | ui | Notification delivery status values are visually distinguishable |

## Verification Steps

**`F210` — The audit viewer renders all required columns for each ledger entry** _(AC1, ui)_

1. Render the AuditLog with the endpoint mocked to return entries for a Transfer and a LoanApplication
1. Assert both entries are rendered as rows
1. Assert each row displays timestamp, actor, action, entity type and entity reference

**`F211` — Audit filters re-query the endpoint with the chosen entity type and date range** _(AC2, ui)_

1. Render the AuditLog and select entity type 'Transfer'
1. Assert GET /api/v1/admin/audit was called with entity_type=Transfer
1. Apply a date range filter and assert the endpoint was called with the from and to values
1. Assert the rendered rows update to the filtered payload

**`F212` — The audit viewer exposes no edit or delete affordance** _(AC3, security)_

1. Render the AuditLog with several entries
1. Assert no button or link with an edit, delete or remove accessible name is present
1. Run: grep -niE 'delete|put|patch|post' frontend/src/pages/admin/AuditLog.tsx
1. Assert no mutating API call against the audit resource is found

**`F213` — The notification viewer renders channel, event type and status for each entry** _(AC4, ui)_

1. Render the Notifications screen with the endpoint mocked to return a transfer event and a loan transition event
1. Assert both entries are rendered as rows
1. Assert each row displays channel, event_type and status

**`F214` — Notification delivery status values are visually distinguishable** _(AC4, ui)_

1. Render the Notifications screen with entries in QUEUED, SENT and FAILED status
1. Assert all three rows render
1. Assert the FAILED entry is rendered with a distinct status treatment from SENT
1. Assert the status is conveyed by text and not by colour alone
