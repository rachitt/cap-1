## Description

Delivers AC-06 as a standalone saved-payee feature. Per DR-17 nothing here gates a transfer. Removal is a soft delete so historical transfer and audit references are never orphaned. Add and remove each write an audit entry, and every operation is scoped to the owning customer per DR-12.

## Acceptance Criteria

**AC1.** `add_beneficiary` persists a beneficiary for the calling customer with a nickname, beneficiary name and account number, returns it with a non-null id and a null `deleted_at`, and appends an audit entry with `action='BENEFICIARY_ADDED'` (AC-06, AC-09).

| Feature | Category | Verifies |
|---|---|---|
| `F096` | functional | Adding a beneficiary persists the record and writes a matching audit entry |

**AC2.** `list_beneficiaries` returns only the calling customer's non-deleted beneficiaries, excluding those belonging to other customers (DR-12).

| Feature | Category | Verifies |
|---|---|---|
| `F097` | security | Beneficiary listing is scoped to the owning customer |

**AC3.** `remove_beneficiary` performs a soft delete by setting `deleted_at`, so the row still exists in the table but is excluded from `list_beneficiaries`, preserving historical references (assumption A-07).

| Feature | Category | Verifies |
|---|---|---|
| `F098` | functional | Removing a beneficiary sets deleted_at and hides it from listings without deleting the row |
| `F099` | integration | A soft-deleted beneficiary leaves earlier audit and transfer records intact |

**AC4.** Attempting to remove another customer's beneficiary raises an ownership error and leaves that beneficiary active (DR-12, edge case E-19).

| Feature | Category | Verifies |
|---|---|---|
| `F100` | security | Removing another customer's beneficiary raises an ownership error |

**AC5.** Re-adding an account number the customer already has as an active beneficiary is rejected as a duplicate; this is an implementation detail for list coherence, not a rule the brief states.

| Feature | Category | Verifies |
|---|---|---|
| `F101` | functional | A duplicate active beneficiary account number for the same customer is rejected |

## Verification Steps

**`F096` — Adding a beneficiary persists the record and writes a matching audit entry** _(AC1, functional)_

1. Call add_beneficiary as customer A with nickname='Mum' and a valid destination account_number
1. Assert the returned record has a non-null id and deleted_at is None
1. Query audit_entries for entity_type='Beneficiary' and the new id
1. Assert exactly one entry exists with action == 'BENEFICIARY_ADDED' and actor_id equal to customer A

**`F097` — Beneficiary listing is scoped to the owning customer** _(AC2, security)_

1. Add one beneficiary as customer A and one as customer B
1. Call list_beneficiaries as B
1. Assert exactly one record is returned and it is B's
1. Assert A's beneficiary id does not appear in B's result

**`F098` — Removing a beneficiary sets deleted_at and hides it from listings without deleting the row** _(AC3, functional)_

1. Add a beneficiary as customer A and call remove_beneficiary on it
1. Call list_beneficiaries for A and assert the removed beneficiary is absent
1. Query the beneficiaries table directly by id and assert the row still exists
1. Assert its deleted_at is a non-null datetime

**`F099` — A soft-deleted beneficiary leaves earlier audit and transfer records intact** _(AC3, integration)_

1. Add a beneficiary, complete a transfer to that account, then remove the beneficiary
1. Query the transfers table for the completed transfer and assert the row is still readable
1. Assert the audit entry for BENEFICIARY_ADDED is still present and unmodified

**`F100` — Removing another customer's beneficiary raises an ownership error** _(AC4, security)_

1. Add a beneficiary as customer A
1. Call remove_beneficiary as customer B with A's beneficiary id inside pytest.raises(OwnershipError)
1. Assert the error is raised
1. Re-read A's beneficiary and assert deleted_at is still None

**`F101` — A duplicate active beneficiary account number for the same customer is rejected** _(AC5, functional)_

1. Add a beneficiary with account_number 'ACC-1001' as customer A
1. Add the same account_number again as customer A inside pytest.raises for the duplicate error
1. Assert the error is raised
1. Assert exactly one active beneficiary row exists for that account number and customer

---

_Epic context: Sprint group G3 (payments). Delivers AC-04, AC-05, AC-06 and the AC-10 notification module. Per DR-17 beneficiaries are an independent convenience feature and are NOT a precondition of a transfer; AC-04 permits a transfer to any valid active account. Per DR-19 no transfer cap, limit or velocity control exists. Atomicity is the single most important correctness property in the system._
