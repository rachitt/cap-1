## Description

The AC-01 onboarding journey in the browser: register, submit KYC, then log in. The critical UX requirement is that a pre-KYC login attempt renders a distinct 'KYC pending' message rather than a generic credentials error, matching the 403 vs 401 distinction the API makes (DR-06).

## Acceptance Criteria

**AC1.** Submitting the registration form with valid details calls `POST /api/v1/auth/register` and navigates to the KYC screen on a 201 response (AC-01).

| Feature | Category | Verifies |
|---|---|---|
| `F174` | ui | Successful registration navigates the customer to the KYC screen |
| `F175` | ui | A duplicate email registration renders a visible field-level error |

**AC2.** The KYC screen submits document type and number, renders the returned verdict, and on a VERIFIED result directs the customer to log in (AC-01).

| Feature | Category | Verifies |
|---|---|---|
| `F176` | ui | A verified KYC result is rendered and directs the customer to login |
| `F177` | ui | A rejected KYC result renders a distinct failure state and does not offer login |

**AC3.** A login attempt receiving 403 with a PENDING_KYC code renders a distinct 'KYC pending' message, while a 401 renders a generic invalid-credentials message (DR-06, edge case E-09).

| Feature | Category | Verifies |
|---|---|---|
| `F178` | ui | A pre-KYC login renders a KYC-pending message distinct from a credentials error |
| `F179` | ui | Invalid credentials render a generic error that does not disclose account existence |

**AC4.** A successful login stores the token and navigates to the dashboard; every form field has a programmatically associated label and validation errors are linked to their input via `aria-describedby`.

| Feature | Category | Verifies |
|---|---|---|
| `F180` | ui | Successful login stores the token and routes to the dashboard |
| `F181` | ui | All onboarding form inputs have associated labels and linked error messages |

## Verification Steps

**`F174` — Successful registration navigates the customer to the KYC screen** _(AC1, ui)_

1. Render the Register screen and fill email, password, full name and date of birth
1. Submit the form with the register endpoint mocked to return 201
1. Assert POST /api/v1/auth/register was called with the entered values
1. Assert the router navigated to the KYC route

**`F175` — A duplicate email registration renders a visible field-level error** _(AC1, ui)_

1. Submit the Register form with the endpoint mocked to return 409
1. Assert an error message is rendered identifying the email as already registered
1. Assert the router did not navigate away from the Register screen

**`F176` — A verified KYC result is rendered and directs the customer to login** _(AC2, ui)_

1. Render the KYC screen and submit a document with the endpoint mocked to return status VERIFIED
1. Assert a success state naming the VERIFIED outcome is rendered
1. Assert a control routing to the login screen is present

**`F177` — A rejected KYC result renders a distinct failure state and does not offer login** _(AC2, ui)_

1. Submit the KYC form with the endpoint mocked to return status REJECTED
1. Assert a failure state is rendered that is visually and textually distinct from the verified state
1. Assert the rejection reason returned by the API is displayed

**`F178` — A pre-KYC login renders a KYC-pending message distinct from a credentials error** _(AC3, ui)_

1. Submit the Login form with the endpoint mocked to return 403 and a PENDING_KYC error code
1. Assert the rendered message refers to pending KYC verification
1. Assert the message text differs from the message rendered for a 401 response

**`F179` — Invalid credentials render a generic error that does not disclose account existence** _(AC3, ui)_

1. Submit the Login form with the endpoint mocked to return 401
1. Assert a generic invalid-credentials message is rendered
1. Assert the message does not state whether the email exists

**`F180` — Successful login stores the token and routes to the dashboard** _(AC4, ui)_

1. Submit the Login form with the endpoint mocked to return 200 and an access_token
1. Assert the token is written to the auth store
1. Assert the router navigated to the dashboard route

**`F181` — All onboarding form inputs have associated labels and linked error messages** _(AC4, ui)_

1. Render each of the Register, KYC and Login screens
1. Assert every input is retrievable by its accessible label via getByLabelText
1. Trigger a validation error and assert the input carries aria-describedby pointing at the error element
1. Run an axe accessibility scan on each screen and assert zero violations
