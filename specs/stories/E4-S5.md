## Description

HTTP surface for AC-04, AC-05 and AC-06. The mapping from domain exception to status code is the contract the frontend depends on to render an unmistakable insufficient-funds state, so each failure mode maps to a specific status and a stable machine-readable error code. Money crosses the boundary as a decimal string per DR-02.

## Acceptance Criteria

**AC1.** `POST /api/v1/beneficiaries` returns 201 with the beneficiary id, `GET /api/v1/beneficiaries` returns 200 listing only the caller's active beneficiaries, and `DELETE /api/v1/beneficiaries/{id}` returns 204 (AC-06).

| Feature | Category | Verifies |
|---|---|---|
| `F116` | functional | Beneficiary create, list and delete return 201, 200 and 204 respectively |
| `F117` | security | Deleting another customer's beneficiary returns 403 and leaves it active |

**AC2.** `POST /api/v1/transfers` returns 201 on success with the transfer id, `status: "COMPLETED"`, and the amount as a JSON string rather than a JSON number (AC-04, DR-02).

| Feature | Category | Verifies |
|---|---|---|
| `F118` | functional | A successful transfer POST returns 201 with COMPLETED status and a string amount |
| `F119` | functional | A transfer to a valid active account not saved as a beneficiary returns 201 |

**AC3.** An insufficient-funds transfer returns 422 with error code `INSUFFICIENT_FUNDS` and leaves the source balance unchanged (AC-05, edge case E-01).

| Feature | Category | Verifies |
|---|---|---|
| `F120` | functional | An over-balance transfer returns 422 with the INSUFFICIENT_FUNDS error code |

**AC4.** A transfer to a non-existent destination returns 404, to a closed destination returns 422, to the caller's own account returns 422, and with a three-decimal-place amount returns 422 (edge cases E-02, E-03, E-06).

| Feature | Category | Verifies |
|---|---|---|
| `F121` | functional | Non-existent and closed destination accounts return 404 and 422 respectively |
| `F122` | functional | Self-transfer and over-precision amounts return 422 with no state change |

**AC5.** `GET /api/v1/transfers` returns 200 with the caller's own transfer history including both COMPLETED and FAILED attempts, and returns 401 without a bearer token (DR-22, DR-33).

| Feature | Category | Verifies |
|---|---|---|
| `F123` | functional | Transfer history returns the caller's completed and failed attempts |
| `F124` | security | GET /api/v1/transfers without a bearer token returns 401 |

## Verification Steps

**`F116` — Beneficiary create, list and delete return 201, 200 and 204 respectively** _(AC1, functional)_

1. POST /api/v1/beneficiaries with a valid nickname and account number and assert status 201 with a non-null id
1. GET /api/v1/beneficiaries and assert status 200 with the new beneficiary present
1. DELETE /api/v1/beneficiaries/{id} and assert status 204
1. GET /api/v1/beneficiaries again and assert the deleted beneficiary is absent

**`F117` — Deleting another customer's beneficiary returns 403 and leaves it active** _(AC1, security)_

1. Create a beneficiary as customer A
1. Authenticate as customer B and DELETE /api/v1/beneficiaries/{A_beneficiary_id}
1. Assert the response status is 403
1. GET /api/v1/beneficiaries as A and assert the beneficiary is still listed

**`F118` — A successful transfer POST returns 201 with COMPLETED status and a string amount** _(AC2, functional)_

1. Fund an account and POST /api/v1/transfers with amount '250.00' to a valid active destination
1. Assert the response status is 201
1. Assert the body status == 'COMPLETED' and id is non-null
1. Assert json.loads gives the amount field as a str instance equal to '250.00', not a float

**`F119` — A transfer to a valid active account not saved as a beneficiary returns 201** _(AC2, functional)_

1. Fund account A and identify an active account B that A has not saved as a beneficiary
1. POST /api/v1/transfers from A to B's account number
1. Assert the response status is 201 and not 403
1. Assert the body status is 'COMPLETED'

**`F120` — An over-balance transfer returns 422 with the INSUFFICIENT_FUNDS error code** _(AC3, functional)_

1. Fund an account with 100.00 and POST /api/v1/transfers with amount '500.00'
1. Assert the response status is 422
1. Assert the body error code equals 'INSUFFICIENT_FUNDS'
1. GET /api/v1/accounts and assert the balance is still the string '100.00'

**`F121` — Non-existent and closed destination accounts return 404 and 422 respectively** _(AC4, functional)_

1. POST /api/v1/transfers to an account number that does not exist and assert the response status is 404
1. POST /api/v1/transfers to an account whose status is CLOSED and assert the response status is 422
1. Assert the source balance is unchanged after both attempts

**`F122` — Self-transfer and over-precision amounts return 422 with no state change** _(AC4, functional)_

1. POST /api/v1/transfers where source and destination are the caller's same account and assert status 422
1. POST /api/v1/transfers with amount '10.001' and assert status 422
1. Assert no transfer with amount 10.00 was created
1. Assert the source balance is unchanged

**`F123` — Transfer history returns the caller's completed and failed attempts** _(AC5, functional)_

1. Execute one successful transfer and one insufficient-funds attempt as customer A
1. GET /api/v1/transfers as A and assert status 200
1. Assert the response includes one entry with status COMPLETED and one with status FAILED
1. Assert no transfer belonging to another customer appears

**`F124` — GET /api/v1/transfers without a bearer token returns 401** _(AC5, security)_

1. GET /api/v1/transfers with no Authorization header
1. Assert the response status is 401
1. Assert the response body contains no transfer data
